This is a daily automated check for the Rent Searcher project (Vietnamese rental-listing aggregator) running in this exact project directory. Everything you need is already here: rebuild_final.py (the Python source that generates vietnam-rent-finder.html), the build_pins_step2_geocode.py -> build_leaflet_data.py -> rebuild_final.py pipeline, and many existing new_listingsNN.py batch files you can read as style/format examples. This check covers the OTHER 7 cities in the system, not Ho Chi Minh City -- HCMC has its own separate, more frequent daily_hcmc_check_prompt.txt/routine, don't duplicate its work here.

GOAL: find genuinely NEW rental listings posted in roughly the last 1-3 days, across all 7 cities below, and add them if found. This runs once a day and covers much more ground than the HCMC check -- it is fine, expected, and NOT a failure if several cities turn up nothing on a given day. Prioritize accuracy over exhaustiveness: it's fine to spend little or no time on a city that's clearly dry today rather than forcing results. Never pad with old or invented listings.

⚠️ CRITICAL GOTCHA -- READ BEFORE TOUCHING EITHER SOURCE'S LOCATION FILTERS:
Vietnam merged/renamed provinces and wards in mid-2025 (63→34 provinces, districts/wards consolidated and renamed). The two scraping sources have NOT kept the same map version:
- Chợ Tốt (nhatot.com / gateway.chotot.com) is STUCK ON THE OLD (pre-2025) structure -- its region_v2/area_v2/ward codes and URL slugs are all old province/city/ward names. The new (current) ward name only shows up inside an individual ad's `ward_name_v3` field, it is NOT filterable.
- Batdongsan.com.vn has MOVED TO THE NEW (post-2025) structure -- its URL slugs (tinh-X/tp-X for province, phuong-X for ward) use the current merged provinces and renamed wards.
This means for a given city, the ward names you filter by on Chợ Tốt and the ward names in Batdongsan URLs will often NOT match each other, and neither will always match this project's own district `key`/`name` list below (which mostly uses the new 2025 names, since that's the current reality on the ground). This is NOT a bug or a sign you have the wrong code -- it's a real source discrepancy. When it happens: use Chợ Tốt's old-structure code to fetch by CITY (area_v2), skip trying to force exact ward-level Chợ Tốt filters where no clean mapping exists, and instead read each ad's actual address/description text to decide which of this project's district keys (below) it belongs to -- exactly like every existing new_listingsNN.py batch file already does. Ward-level Chợ Tốt codes are given below where they were verified; treat them as a nice-to-have narrowing filter, not a requirement.

SOURCE ACCESS -- general mechanics (same across all cities):
- Chợ Tốt: plain WebFetch gets 403'd on nhatot.com pages, but the public JSON gateway API works with no auth: `https://gateway.chotot.com/v1/public/ad-listing?cg=<cat>&region_v2=<code>&area_v2=<code>&st=u&limit=20&o=<offset>` and `.../ad-listing/<list_id>` for a single ad. Gives exact `orig_list_time`, `ward_name_v3`, price, size, seller. Categories (verified live against the API -- the previous note here had two of these WRONG, which silently cost the project every room listing for months, so do not "correct" them back from memory): **1010** = Căn hộ/Chung cư (apartments), **1020** = Nhà ở (houses), **1030** = Văn phòng, Mặt bằng kinh doanh (offices and retail/commercial premises), **1040** = Đất (land), **1050** = Phòng trọ (ROOMS -- this is residential and IS in scope; an older version of this prompt wrongly called it office/retail and told you to skip it), and **1060 returns nothing at all** -- do not query it, an older version of this prompt wrongly used it for rooms. Fetch 1010, 1020, 1050 for residential. COMMERCIAL: also fetch **1030** -- the project now covers commercial premises as well as housing. File those with one of three types, chosen by what the ad actually describes: "Офис" (office, văn phòng), "Торговая площадь" (retail unit / shopfront / street-front commercial space -- mặt bằng kinh doanh, MB, mặt tiền; this is the most common by far), or "Склад" (warehouse / light-industrial -- kho, kho xưởng, nhà xưởng). If genuinely ambiguous use "Торговая площадь". NOTE ON PRICE RANGE: commercial rents run far above residential -- sampled Q7 ads ranged from 3.5 million to 160 million VND/month, and the site's budget slider only reaches 45 million, so do not discard a listing merely because it looks expensive; record the real price. Everything else about a commercial listing -- price/area verification, ward assignment, the RU and EN description pair, photos -- follows exactly the same rules as a residential one.
- Batdongsan: WebFetch gets 403'd, but plain `curl` with a browser User-Agent usually returns 200 (occasionally still 403s -- retry once before giving up). When parsing listing cards from a search-results page, split on `<div class="js__card js__card-full-web` -- splitting on `re__card-image` instead causes an off-by-one where each card gets the *previous* card's price.
- Facebook (Marketplace and groups): curl gets HTTP 400, WebFetch hits a login wall. Expect this to fail every run in this headless environment -- note it in the report rather than spending much time on it.
- UNICODE TRAP when matching `ward_name_v3` (or any ward name) against this project's district names: the gateway API returns `ward_name_v3` in inconsistent Unicode normalization (mixing precomposed NFC and decomposed NFD Vietnamese diacritics). A naive Python string comparison (`==` or plain substring match) silently misses most true matches -- one HCMC run found only 24 candidates before normalizing vs. 54 after fixing this. Always run both sides through `unicodedata.normalize('NFC', s)` (or NFD, just be consistent) before comparing ward names.
If a source is fully inaccessible today, say so plainly in your final report rather than skipping it silently or inventing data.

RE-PUSH DATE TRAP (important, easy to get wrong): both Chợ Tốt and Batdongsan let sellers "re-push" (đẩy tin) old ads, which resets the *displayed* date without it being a new listing. For Chợ Tốt, always compute daysAgo from `orig_list_time`, never `list_time` (list_time is the bumped/re-pushed time). Batdongsan publishes no original date at all, so for it: only accept ads whose product ID (`-prNNNNNNNN` in the URL) is in the current-day range, confirm the price twice (search-results card AND the detail page, where the field is labeled `Khoảng giá`, not `Mức giá`), and record in the listing's details notice that the date shown is just the site's own relative stamp, not a verified post date.

MISSING orig_list_time (measured 31 Aug 2026, 400 live HCMC ads across cg=1010 and cg=1020): Chợ Tốt omits `orig_list_time` entirely on 138 of 400 ads -- 34.5%, not a rare edge case, and the single-ad detail endpoint omits it for exactly the same ads, so re-fetching does not recover it. Some of those are genuinely minutes old; others are plainly old ads re-pushed, e.g. list_id 115489272 displayed as "20 phút trước" while current ids are ~134.4M. WHEN orig_list_time IS ABSENT YOU CANNOT ESTABLISH THE ORIGINAL POST DATE FROM THIS API AT ALL. Do not fall back to `list_time` -- that is precisely the re-push trap this section exists to prevent. Skip the ad. Do not try to rescue it with the list_id either: that was tested and does not work -- ads verified at <=1 day old span an id gap of 5,051 to 1,933,184 below the newest id, while ads verified at >7 days old start at 119,509, so the two ranges overlap and the id separates nothing in either direction. If you keep such an ad anyway because it is otherwise valuable, you must set daysAgo conservatively (assume it is old, not new) AND say in `details.notice` / `noticeEn` that the posting date could not be verified -- the same honesty the Batdongsan rule above requires. Never let an unverifiable date be recorded as a fresh one. A ready-made checker exists: `python check_freshness.py <list_id> ...` (also `--from-json candidates.json`, `--from-file ids.txt`, `--in-base`). It prints FRESH / STALE / UNVERIFIABLE per ad and, for fresh ones, the exact `daysAgo=` and `posted="..."` values to write, so the date is never re-derived by eye; it exits non-zero unless every ad checked is FRESH. Run it on your candidates before writing any L(...) rather than trusting whatever a fetch script happened to print -- the five mis-dated listings of 31 Aug 2026 had `orig_list_time` sitting in the responses all along, but the script that printed them showed subject/price/ward and not that field.

CHỢ TỐT GIVES YOU COORDINATES -- DO NOT GEOCODE NEW LISTINGS. Every ad carries `latitude` and `longitude`, in both the search-listing and the single-ad responses. Add them to `chotot_coords.json` (a tracked JSON object, commit it with the batch) as `{"<key>": {"lat": ..., "lon": ...}}` where `<key>` is either the site listing id (e.g. `"2000440"`) or the Chợ Tốt ad id from the URL (`/134473943.htm` -> `"134473943"`) -- both are accepted, the pipeline matches on whichever it finds -- merge into the existing object, never overwrite the file. That is the ONLY place source coordinates survive: `build_pins_step2_geocode.py` reads this file, records those ids with `"source": "chotot"` and never sends them to Nominatim, and `build_leaflet_data.py` treats them as precise. Do NOT write into `leaflet_listing_latlon.json` or `pin_results.json` by hand -- both are regenerated from scratch on every pipeline run and anything written there is silently discarded (this is exactly what happened to every coordinate written that way before 2 Sep 2026). This is strictly better than geocoding the description: most older entries sit on a ward centroid (`"geocoded": false`), and free-text geocoding fails in ways that raise no error -- on 31 Aug 2026 Nominatim silently returned the SAME factory as the centre of two different Bình Dương districts, which would have stacked two districts on one map pin.

CHỢ TỐT HAS NO URL FIELD, AND THE LINK CANNOT BE VERIFIED -- nhatot.com answers 403 to any request, browser User-Agent included, so do not try to check a link by fetching it. Build it: `https://www.nhatot.com/thue-{cat}-{slug(area_name)}-{slug(region_name)}/{list_id}.htm`, where cat is `can-ho-chung-cu` for cg=1010, `nha-dat` for cg=1020, `phong-tro` for cg=1050, `van-phong-mat-bang-kinh-doanh` for cg=1030, and slug() strips diacritics (NFD, drop combining marks), maps đ→d, lowercases, and replaces every run of non-alphanumerics with a hyphen. This rule was derived from the 54 URL forms already stored in the site and checked in reverse -- regenerating links for cities whose URLs are already known reproduced 59 of them exactly, and every mismatch was a district the site does not cover. If you invent a different slug shape, listings will point at 404s and nothing in the build will tell you.

CRITICAL RULES (this project has a zero-tolerance history on these -- read a few recent new_listingsNN.py files first to absorb the house style and these conventions in practice):
- NEVER fabricate a listing, price, address, or URL. If you can't verify a real price anywhere (displayed field AND description), set price to Python None and add a details notice "цена по запросу" (price on request) rather than guessing.
- Known site quirk: Facebook's displayed price field is frequently exactly 10x (or more) lower than the price stated in the description text -- always read the full description and use ITS price, noting the discrepancy if one exists.
- Compute daysAgo honestly from today's real date (run `date` if unsure) vs the listing's real stated post date. Do not include anything older than 14 days (project-wide rule, applies here too).
- Before adding anything, grep rebuild_final.py for its URL -- if the exact URL already exists anywhere in the file, it's a duplicate, skip it (regardless of which batch/source/city added it originally). EXCEPTION -- price change: if you happen to notice an existing URL's CURRENT price (from today's fetch) differs from what's stored in rebuild_final.py, that's a real signal worth capturing (price drops are useful negotiating leverage for the user). Append `{"price":<old_price>,"date":"<today>"}` to that listing's `details.priceHistory` array (create it if absent), then update the listing's own price field to the new value. Still don't create a new L() entry for it. Don't go out of your way hunting for these -- only act on it when a URL you already happen to be looking at (e.g. while scanning for new candidates) happens to be one already in the file.
- CROSS-SOURCE DUPLICATES (same property, different platform/agent, different URL): if a new candidate shares city+district+type+price+area with an EXISTING listing AND the description names the same street/building/lot dimensions, it's the same physical property re-posted, not a new listing. Don't add it as a separate card. Instead add it to the existing listing's `details.alsoOn` list (`{"source":"...","url":"..."}`) -- create that key if it doesn't exist yet -- and skip creating a new L() entry. This is how the project already collapsed 6 known clusters (see the "Cross-source duplicate linking" commit) -- be conservative: only merge on a real shared identifier (exact street name, distinctive lot size), never on price+area coincidence alone.
- TELEGRAM SOURCES -- ALWAYS STORE THE PERMALINK, NEVER THE CHANNEL URL. If you add a listing found in a public Telegram channel, its `url` must point at that specific post (`https://t.me/<channel>/<message_id>`), never at the channel (`https://t.me/s/<channel>`). Every telegram listing currently in the base stores only the channel URL, so there is nothing unique to compare against and duplicate-detection for this source is impossible by construction -- the same flat can be re-added on every run. When a post carries a stable agency id such as "ID A2249", put it in `details.notice`: it is the most reliable dedup key these channels offer. `fetch_telegram_listings.py` harvests candidates from the readable channels and already emits both fields; it never writes to rebuild_final.py, so district assignment and the RU/EN description pair stay your judgement.
- LISTING TYPE IS A CLOSED SET. Use exactly one of "Комната", "Студия", "Квартира", "Дом", "Другое" for housing, or "Офис", "Торговая площадь", "Склад" for commercial. Do NOT invent a more specific variant. On 31 Aug 2026 a run produced 29 listings typed "1/2/3-спальная квартира"; the site's type filter compares strictly and draws one chip per allowed type, so those listings were unreachable for anyone who narrowed by type while their cards still rendered perfectly -- nothing looked wrong to whoever added them. Put the bedroom count in the description, where it belongs. rebuild_final.py now FAILS THE BUILD on an unknown type (check_listing_types), so this stops you instead of shipping silently -- but do not rely on the guard to think for you.
- Descriptions should be in Russian, matching the rest of the project's voice (concise, factual: price/area/location/amenities, honest notices for any data quirks). Every listing MUST also carry an English description via the `descEn=` keyword argument on L(...), AND every `details` dict that has a `"notice"` MUST carry a `"noticeEn"` alongside it -- the site is bilingual (RU/EN toggle, and a separate en.html indexed by search engines), and English is what most foreign renters in Vietnam actually search in.
