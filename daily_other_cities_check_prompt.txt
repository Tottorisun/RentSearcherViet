This is a daily automated check for the Rent Searcher project (Vietnamese rental-listing aggregator) running in this exact project directory. Everything you need is already here: rebuild_final.py (the Python source that generates vietnam-rent-finder.html), the build_pins_step2_geocode.py -> build_leaflet_data.py -> rebuild_final.py pipeline, and many existing new_listingsNN.py batch files you can read as style/format examples. This check covers the OTHER 7 cities in the system, not Ho Chi Minh City -- HCMC has its own separate, more frequent daily_hcmc_check_prompt.txt/routine, don't duplicate its work here.

GOAL: find genuinely NEW rental listings posted in roughly the last 1-3 days, across all 7 cities below, and add them if found. This runs once a day and covers much more ground than the HCMC check -- it is fine, expected, and NOT a failure if several cities turn up nothing on a given day. Prioritize accuracy over exhaustiveness: it's fine to spend little or no time on a city that's clearly dry today rather than forcing results. Never pad with old or invented listings.

⚠️ CRITICAL GOTCHA -- READ BEFORE TOUCHING EITHER SOURCE'S LOCATION FILTERS:
Vietnam merged/renamed provinces and wards in mid-2025 (63→34 provinces, districts/wards consolidated and renamed). The two scraping sources have NOT kept the same map version:
- Chợ Tốt (nhatot.com / gateway.chotot.com) is STUCK ON THE OLD (pre-2025) structure -- its region_v2/area_v2/ward codes and URL slugs are all old province/city/ward names. The new (current) ward name only shows up inside an individual ad's `ward_name_v3` field, it is NOT filterable.
- Batdongsan.com.vn has MOVED TO THE NEW (post-2025) structure -- its URL slugs (tinh-X/tp-X for province, phuong-X for ward) use the current merged provinces and renamed wards.
This means for a given city, the ward names you filter by on Chợ Tốt and the ward names in Batdongsan URLs will often NOT match each other, and neither will always match this project's own district `key`/`name` list below (which mostly uses the new 2025 names, since that's the current reality on the ground). This is NOT a bug or a sign you have the wrong code -- it's a real source discrepancy. When it happens: use Chợ Tốt's old-structure code to fetch by CITY (area_v2), skip trying to force exact ward-level Chợ Tốt filters where no clean mapping exists, and instead read each ad's actual address/description text to decide which of this project's district keys (below) it belongs to -- exactly like every existing new_listingsNN.py batch file already does. Ward-level Chợ Tốt codes are given below where they were verified; treat them as a nice-to-have narrowing filter, not a requirement.

SOURCE ACCESS -- general mechanics (same across all cities):
- Chợ Tốt: plain WebFetch gets 403'd on nhatot.com pages, but the public JSON gateway API works with no auth: `https://gateway.chotot.com/v1/public/ad-listing?cg=<cat>&region_v2=<code>&area_v2=<code>&st=u&limit=20&o=<offset>` and `.../ad-listing/<list_id>` for a single ad. Gives exact `orig_list_time`, `ward_name_v3`, price, size, seller. Categories: 1010 căn hộ (apartment), 1020 nhà ở (house), 1060 phòng trọ (room) -- 1050 is office/retail, skip it, not residential.
- Batdongsan: WebFetch gets 403'd, but plain `curl` with a browser User-Agent usually returns 200 (occasionally still 403s -- retry once before giving up). When parsing listing cards from a search-results page, split on `<div class="js__card js__card-full-web` -- splitting on `re__card-image` instead causes an off-by-one where each card gets the *previous* card's price.
- Facebook (Marketplace and groups): curl gets HTTP 400, WebFetch hits a login wall. Expect this to fail every run in this headless environment -- note it in the report rather than spending much time on it.
- UNICODE TRAP when matching `ward_name_v3` (or any ward name) against this project's district names: the gateway API returns `ward_name_v3` in inconsistent Unicode normalization (mixing precomposed NFC and decomposed NFD Vietnamese diacritics). A naive Python string comparison (`==` or plain substring match) silently misses most true matches -- one HCMC run found only 24 candidates before normalizing vs. 54 after fixing this. Always run both sides through `unicodedata.normalize('NFC', s)` (or NFD, just be consistent) before comparing ward names.
If a source is fully inaccessible today, say so plainly in your final report rather than skipping it silently or inventing data.

RE-PUSH DATE TRAP (important, easy to get wrong): both Chợ Tốt and Batdongsan let sellers "re-push" (đẩy tin) old ads, which resets the *displayed* date without it being a new listing. For Chợ Tốt, always compute daysAgo from `orig_list_time`, never `list_time` (list_time is the bumped/re-pushed time). Batdongsan publishes no original date at all, so for it: only accept ads whose product ID (`-prNNNNNNNN` in the URL) is in the current-day range, confirm the price twice (search-results card AND the detail page, where the field is labeled `Khoảng giá`, not `Mức giá`), and record in the listing's details notice that the date shown is just the site's own relative stamp, not a verified post date.

CRITICAL RULES (this project has a zero-tolerance history on these -- read a few recent new_listingsNN.py files first to absorb the house style and these conventions in practice):
- NEVER fabricate a listing, price, address, or URL. If you can't verify a real price anywhere (displayed field AND description), set price to Python None and add a details notice "цена по запросу" (price on request) rather than guessing.
- Known site quirk: Facebook's displayed price field is frequently exactly 10x (or more) lower than the price stated in the description text -- always read the full description and use ITS price, noting the discrepancy if one exists.
- Compute daysAgo honestly from today's real date (run `date` if unsure) vs the listing's real stated post date. Do not include anything older than 14 days (project-wide rule, applies here too).
- Before adding anything, grep rebuild_final.py for its URL -- if the exact URL already exists anywhere in the file, it's a duplicate, skip it (regardless of which batch/source/city added it originally). EXCEPTION -- price change: if you happen to notice an existing URL's CURRENT price (from today's fetch) differs from what's stored in rebuild_final.py, that's a real signal worth capturing (price drops are useful negotiating leverage for the user). Append `{"price":<old_price>,"date":"<today>"}` to that listing's `details.priceHistory` array (create it if absent), then update the listing's own price field to the new value. Still don't create a new L() entry for it. Don't go out of your way hunting for these -- only act on it when a URL you already happen to be looking at (e.g. while scanning for new candidates) happens to be one already in the file.
- CROSS-SOURCE DUPLICATES (same property, different platform/agent, different URL): if a new candidate shares city+district+type+price+area with an EXISTING listing AND the description names the same street/building/lot dimensions, it's the same physical property re-posted, not a new listing. Don't add it as a separate card. Instead add it to the existing listing's `details.alsoOn` list (`{"source":"...","url":"..."}`) -- create that key if it doesn't exist yet -- and skip creating a new L() entry. This is how the project already collapsed 6 known clusters (see the "Cross-source duplicate linking" commit) -- be conservative: only merge on a real shared identifier (exact street name, distinctive lot size), never on price+area coincidence alone.
- TELEGRAM SOURCES -- ALWAYS STORE THE PERMALINK, NEVER THE CHANNEL URL. If you add a listing found in a public Telegram channel, its `url` must point at that specific post (`https://t.me/<channel>/<message_id>`), never at the channel (`https://t.me/s/<channel>`). Every telegram listing currently in the base stores only the channel URL, so there is nothing unique to compare against and duplicate-detection for this source is impossible by construction -- the same flat can be re-added on every run. When a post carries a stable agency id such as "ID A2249", put it in `details.notice`: it is the most reliable dedup key these channels offer. `fetch_telegram_listings.py` harvests candidates from the readable channels and already emits both fields; it never writes to rebuild_final.py, so district assignment and the RU/EN description pair stay your judgement.
- Descriptions should be in Russian, matching the rest of the project's voice (concise, factual: price/area/location/amenities, honest notices for any data quirks). ALSO provide an English description via the `descEn=` keyword argument on L(...) -- the site is bilingual (RU/EN toggle, and a separate en.html indexed by search engines), and English is what most foreign renters in Vietnam actually search in. Keep descEn a faithful, equally concise translation of desc -- same facts, same numbers, no embellishment; transliterate Vietnamese place names as they appear (Thao Dien, Phu My Hung) rather than translating them. If you genuinely cannot produce a sound English version, omit descEn rather than guessing -- the site falls back to the Russian text.
- Assign each listing to the correct project district `key` (e.g. "vh", "xh", "hc"...) by reading its actual address/description, not by which source-side location filter happened to return it -- this matters especially given the old/new naming mismatch described above.
- PHOTOS ARE A CORE FEATURE, NOT OPTIONAL -- this is meant to compete with real listing sites (Avito-style), and a card with no photo is a real product gap. For Chợ Tốt specifically, capturing photos is REQUIRED, not best-effort: its gateway API already returns the full `images` array on every ad you fetch for verification -- grab up to 3 of them (`details={"photos": ["url1","url2","url3"]}`), it costs no extra request. For Batdongsan, try the listing page's `<img>` tags (usually `file4.batdongsan.com.vn/...`) but don't fight it -- if Cloudflare's challenge is blocking that run (check for `Cf-Mitigated: challenge` in response headers), just skip photos for that batch rather than burning time, it's a known intermittent block, not a bug to fix here. Never invent or substitute a stock/placeholder image; if no real photo URL is available after a reasonable try, omit the `photos` key entirely (the card renders fine without one).

INTEGRATION STEPS (follow the file's own established pattern exactly):
1. ID ALLOCATION -- RESERVE YOUR IDS, NEVER PICK THEM YOURSELF. Run:
   `python allocate_ids.py --block 2000000 --count <how many listings you are adding> --owner other-cities-daily`
   It prints `FIRST=<n> LAST=<m>`. Use exactly those ids, in order, and no others.
   If your run is long, re-run `python allocate_ids.py --renew FIRST-LAST` occasionally so your
   reservation cannot expire while you are still working.
   Once the listings are actually written into rebuild_final.py, run
   `python allocate_ids.py --release FIRST-LAST`.
   If allocation fails it exits non-zero with a message -- STOP and report it. Never fall back to
   guessing an id: a silently wrong id resurfaces as a duplicate a week later.
   REASON: picking ids yourself -- even from your own block, even re-reading the max at write time --
   still collides when two instances of THIS SAME check overlap, because both read the same max and
   both start there; and it cannot see ids already reserved by another run but not yet written to the
   file. That collision has corrupted this dataset four times, breaking favourites, the details
   toggle, and everything else keyed by listing id. allocate_ids.py serialises allocation with an
   atomic lock and tracks outstanding reservations, closing both holes. Never renumber or touch ids
   you were not given. Before committing, still assert uniqueness across the whole file:
   `python -c "import re,collections;i=[int(x) for x in re.findall(r'^L\((\d+),',open('rebuild_final.py',encoding='utf-8').read(),re.M)];d=[k for k,v in collections.Counter(i).items() if v>1];print('DUPLICATE IDS:',d) if d else print('ids unique:',len(i))"`
   If it reports duplicates, stop and report rather than committing.
2. Find the highest-numbered existing `new_listingsNN.py` file in this directory; your new file is the next number.
3. Write `new_listings<N>.py` following the EXACT pattern of the existing ones (open a recent one, e.g. the highest-numbered file, and copy its structure verbatim): a NEW_SRC string of `L(id,"<city_key>","<ward_key>","<Комната|Студия|Квартира|Дом>",price_or_None,area_or_None,\n  "russian description",\n  "url","posted text",daysAgo,source="...",\n  details={...}),` entries, then the same marker-replace boilerplate (`marker = "]\n\n# Real lat/lon"`) used in every prior batch file in this repo.
4. Run `python new_listings<N>.py` to insert into rebuild_final.py.
5. Run `python purge_old_listings.py` -- recomputes every listing's TRUE current age from `posted_dates.json` (a persisted first-seen-date cache, git-history-backfilled once) and physically removes any `L(...)` block older than 14 days, updating `daysAgo`/`posted` text in place for everything that stays. Run this BEFORE the first rebuild so the purge is reflected everywhere downstream. It prints which IDs it removed -- if it ever removes an unexpectedly large fraction of the file, stop and investigate rather than proceeding.
6. Run `python rebuild_final.py` FIRST -- `build_pins_step2_geocode.py` parses `var DATA = {...}` out of the *built* `vietnam-rent-finder.html`, not out of `rebuild_final.py`'s source, so the new rows must already be baked into the HTML before geocoding sees them. Skipping this step doesn't error -- it silently geocodes the stale HTML and the new listings end up with no coordinates.
7. Then run, in this order: `python build_pins_step2_geocode.py` (geocodes new addresses via Nominatim, rate-limited ~1.1s/query, already cached for anything seen before) -> `python build_leaflet_data.py` -> `python rebuild_final.py` again (final bake-in of the real lat/lon).
8. Sanity check: the `listings with lat/lon: N` line that `build_leaflet_data.py` prints should match `grep -cP "^L\(" rebuild_final.py` (total listing count) -- if it matches the PRE-insert count instead, step 6 was skipped or ran too late. Also confirm the new listing count matches what you added (minus anything the step-5 purge removed) and that there are zero duplicate URLs in the final LISTINGS array. Also verify zero `"duplicateOf":<id>` references point at an id no longer present in the file -- the purge step can orphan a cross-source-dedup secondary if its primary aged out; if that happens, strip the dangling `"duplicateOf":N,` so the orphaned listing becomes visible again standalone. Also check `rebuild_final.py`'s own output for a `WARNING: possibly-undefined JS function calls` line -- it runs automatically on every rebuild and would flag something like a stray call to a function that doesn't exist (this happened for real once, from a stash/merge conflict silently reviving deleted code, and broke city switching in production with no other symptom). If you see that warning and didn't touch any JS yourself this run, stop and investigate before committing.

IF AND ONLY IF you added at least one genuinely new, verified listing, OR the step-5 purge actually removed at least one aged-out listing:
9. `git add -A && git commit -m "..."` describing what changed (mention added-count and cities, and/or purged-count if anything aged out), then `git push` (the repo already has a GitHub remote configured with working credentials -- this should just work). Only stage files this run actually touched or intentionally created.
10. Publish the artifact: call the Artifact tool with `file_path` pointing at the rebuilt `vietnam-rent-finder.html`, `url: "https://claude.ai/code/artifact/be6f5e7f-84a1-466a-8444-ffac55d827cf"` (this MUST be included -- omitting it creates a stray duplicate artifact instead of updating the real one), `favicon: "🏠"`, and a short `label` describing the day's change. If the Artifact tool is unavailable in this context, skip this step and just note it in your final report -- the git push is what matters most for persistence.

IF NOTHING NEW WAS FOUND ANYWHERE AND NOTHING WAS PURGED (including if all sources were inaccessible today): do NOT commit, do NOT publish -- just say so.

End your final message with a short, human-readable Russian-language summary: how many new listings found (if any) and in which cities/areas, which sources worked vs were blocked today, and confirmation of whether you pushed/published. Keep it concise -- this is a daily status update, not a full report.
